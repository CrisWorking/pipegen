Version 6, 2026-10-29: adds T49 (the tool-cache race), T50 (a secret as a file name) and T51 (a folder swapped during a read). ## What we protect (assets)

| Asset | Why it matters |
|---|---|
| The user's **source code** | It's private and the company's main value |
| The user's **secrets** (API keys, test keys, the signing key, the Slack webhook) | A leak gives an attacker access to systems |
| The user's **CI** (what runs in their GitHub Actions) | Code that runs there can steal secrets or tamper with builds |
| The user's **GitHub account access** (the token pipegen uses) | Too much access = everything can be changed |
| The **gate decision** | If it can be faked, bad code reaches `main` or production |
| **pipegen's own releases**, reviewed list and gate action | One compromise reaches **every** user at once |

## Who could attack (actors)

1. **A malicious tool author / typosquatter**: publishes a tool or action with a name close to a popular one, or buys stars.
2. **A hijacked maintainer** of a real tool: moves a tag to a malicious commit (the tj-actions case, March 2025).
3. **A malicious contributor to the user's repo**: puts hidden instructions in code or docs to steer the AI (prompt injection), or opens a PR that fakes a passing check.
4. **An attacker targeting pipegen itself**: compromises pipegen's npm package, repo, reviewed list or gate action.
5. **A curious insider / mistake**: pastes production keys as "test" keys, or closes the setup PR halfway.

## Entry points and threats → what stops them

| # | Threat | Mitigation in v3 | Residual risk |
|---|---|---|---|
| T1 | The AI is steered into choosing a malicious tool | Blocking tools come **only from the reviewed list**. Live finds are **mention-only** (never run). Security-relevant inputs are fixed by templates, and the AI picks only enums | A reviewed tool that is itself compromised (T3, T26) |
| T2 | Typosquatted or star-farmed tool | Near-duplicate name check against the reviewed list. The quality bar (Scorecard, age, licence, advisories). Unreviewed tools are mention-only (never run) | A new, clean-looking malicious tool can still pass the bar → it's only ever mentioned, never run |
| T3 | A tag moved to a malicious commit | Pins are full SHAs. **A moved tag → stop + alert**, never auto-update. The watcher flags moved tags as urgent | A commit that was malicious from the start and got reviewed (needs maintainer review to slip) |
| T4 | Prompt injection makes the AI write a dangerous command | `StepSpec` validation, no free YAML, referee + actionlint + zizmor, reviewed templates for blocking steps (security-relevant inputs fixed), unreviewed tools never run, change guard (no app code edits) | AI-chosen enum values within reviewed templates |
| T5 | Over-powered token | pipegen's own **GitHub App** first (device flow, installed on "Only select repositories"); fallback: a **fine-grained token** limited to the involved repos (DECISIONS #87). **Classic tokens** and an App installed on **"All repositories"** are refused. An Actions `GITHUB_TOKEN` (`ghs_`) is accepted for the **read-only audit only**. The token goes only to `api.github.com` and is never printed | The user can override the classic / all-repositories refusal with `--allow-broad-token` |
| T6 | Code copied into the scratch repo leaks old secrets from history | **HEAD only, no history**. A private per-project scratch repo. Emptied after proof | Secrets still present in current files (pipegen's own secret scan warns about them in the audit and before the proof) |
| T7 | User workflows run in the scratch repo (deploys, webhooks, cloud OIDC) | **All** user workflows are disabled in scratch. Existing jobs are run only as pipegen-controlled copies without the user's secrets | Cloud trust policies that trust `repo:owner/*` → the README advises pinning OIDC trust to exact repos |
| T8 | A faked passing gate (same-name check) | Verify-first checks: the run of `pipegen.yml`, `event == push`, the same repository, the expected central SHA in `referenced_workflows`, gate job success. The public key comes from the `pipegen-signing` environment variable and must match its hash in the install record (T30). Spike S2: the gate is found through the run's jobs, and `referenced_workflows[].ref` is missing when the central workflow is pinned by SHA (DECISIONS #78) | Runs past retention can't be verified (fails closed). The gate job is bound by its name only: GitHub's API ties no job to the file that defined it, so a writer who gets a changed `pipegen.yml` with an inline job named `pipegen / gate` onto the default branch passes the check (Plan C C8, accepted). The guard is a required code-owner review of `.github/workflows/**` with no bypass; Plan H's drift check detects it |
| T9 | Gate fails open (no baseline, forks) | No baseline → a **same-run base-commit scan** decides what's new (dependency and image findings always). Fingerprints count occurrences. Secret fingerprints are an HMAC per secret | Scanners that can't run on the base commit only warn on installing PRs |
| T10 | The signing key is readable from any branch | The key lives in the `pipegen-signing` environment, which only the default branch may use. Key-based signing needs that rule **proven**, never assumed: pipegen probes the environment and reads back its deployment branch policy (custom policies, exactly one rule, the default branch; the `deploymentBranchPolicies` capability), and anything less means no key-based signing (fail closed). Spike S3 found environments, environment secrets and enforced branch policies on **Free private** repos too, so those can get key-based signing as well (DECISIONS #86, replacing the earlier "no signing on Free private"). `pipegen run` creates the environment and the rule when there is none (only a new one, after consent and before the proof), reads both back, and only then plans key-based signing; delivery reads the rule back again before it stores the key; otherwise: **no signing** (honest) | An admin can change the environment rules. A write collaborator can overwrite the key secret and the public-key variable, so verify compares the key with the hash in the install record (T30, DECISIONS #76). On Free private this contradicts GitHub's docs and may be withdrawn without notice; it is verified by the read-backs at `run` and at delivery, and by `verify` |
| T11 | Secrets leak through logs, AI, PRs, Slack | Never written. Redaction (incl. connection strings) before the AI. Masking in CI. Values wiped from memory after storing | A tool printing a secret in its own logs (CI masking covers registered secrets) |
| T12 | Production keys pasted as test keys | The question says "test keys only". Keys are deleted from scratch after proof. They're stored in the app repo only if the user confirms | The user ignores the warning |
| T13 | Made-up packages (hallucinated deps) | Every added package must exist in its registry and pass the quality bar | A real but malicious package that passes the bar (rare, possible) |
| T14 | Compromise of pipegen's releases or reviewed list | Trusted publishing + provenance, signed tags, rulesets, CODEOWNERS on `data/reviewed-tools.yml` and `gate/`, Scorecard 9+ goal, a second maintainer | A single-maintainer period before a second maintainer joins |
| T15 | The setup PR is closed without merging and a required check blocks the repo | Settings are applied **only after merge** | None known |
| T16 | Runaway costs (Actions minutes, AI) | Estimates at consent, a hard 2× minutes cap, a monthly estimate in `PIPEGEN.md`, audit first | Estimates can be off for unusual repos |


### Added in version 2 (round-2 red team)

| # | Threat | Mitigation in v3.1 | Residual risk |
|---|---|---|---|
| T17 | **A PR rewrites the workflow or scanner config that judges it** (GitHub runs the PR's own workflow files) | The gate blocks PRs touching protected paths unless a CODEOWNER approved. New suppressions are findings. Code-owner review in the ruleset (≥ 2 writers). **Org required workflow** on Team/Enterprise orgs. `pipegen verify` reports drift | **Solo/personal repos:** someone who can merge can weaken the pipeline. It's visible, but it can't be prevented |
| T18 | **Artifact poisoning:** a job uploads a fake "clean" SARIF that the gate trusts | Exact artifact names only. The SARIF sha256 is checked against the producing job's output. Advisory (non-blocking) tools use the same `pipegen-out-` names; the trusted job list says which checks block | A compromised **reviewed** tool can still lie (reviewed-list governance) |
| T19 | **Baseline / clean-run spoofing** from a fork branch named `main` | Accepted only from `push` runs of `pipegen.yml` in the same repository id, with the run id stored in the artifact | A writer who can run a workflow with the `PIPEGEN_FP_KEY` secret can forge a baseline or marker MAC (Plan C ruling B6). A forged marker can only make the gate stricter |
| T20 | **Cache poisoning** by a PR job or another workflow, read later by a gate-feeding, build or sign job | `cache-mode: none` on every job that feeds the gate or builds, signs or verifies; scanners' own caches off | Caches in the user's own jobs stay outside pipegen's control |
| T21 | **Scratch push race:** user workflows fire on push before they're disabled | User workflow files are never pushed (compat copies only). Secrets are stored after that. Egress is limited in proof | None known |
| T22 | **The AI adds code that runs in CI** (scripts, dependencies, tests, Dockerfile), steered by injected text in logs | Fixes are limited to the failing part's files. Script and dependency changes get a separate confirmation. `--ignore-scripts`. No advisory logs in prompts. No secrets for created code beyond the runtime env. Egress limited in proof | A real but malicious package that passes the quality bar |
| T23 | **Secrets in scan artifacts** (scanners copy the found key into the report) | `--redact`, snippets stripped after hashing, scratch runs and artifacts deleted after proof | Logs of user-owned jobs |
| T24 | **Hostile repo content attacks the CLI machine** (symlinks to `~/.aws/credentials`, path tricks) | `lstat`, symlinks never followed, every resolved path checked to stay inside the project | Bugs in archive/parsing libraries |
| T25 | **Token scope not verified** (a fine-grained token may push users to "All repositories") | Decided by spike S1 (DECISIONS #87, #88): pipegen's App on "Only select repositories"; pipegen creates its helper repos itself, and they join that installation. The installation's scope is checked: "All repositories" is refused unless `--allow-broad-token`, and which repos it reaches comes from the installation's own repo list, not from `GET /repos`. In the fine-grained fallback the user creates the 3 repos and scopes the token to them; what the token may do is probed, never read from `GET /repos` `permissions` | A fine-grained token's own repo list can't be read through the API: a public repo outside it still answers reads, so only the permission probes find that gap |
| T26 | **Platform actions or images move** (checkout, upload-artifact, base images) | In the reviewed list with stored SHAs/digests and moved-tag alerts | Same as T3 |
| T27 | **Release hijack** (a stolen maintainer account publishes a bad version, or `npx pipegen` runs whatever is latest) | Tag ruleset, trusted publishing, exact-version instructions (`npx pipegen@x.y.z`, `npm audit signatures`), a 7-day cooldown for gate/watcher/list bumps, a second maintainer goal | A single-maintainer period |

### Added in version 3 (third review)

| # | Threat | Mitigation in v3.2 | Residual risk |
|---|---|---|---|
| T28 | **A commit status fakes the required check** (`POST /statuses`, no file change) | The required check `pipegen / gate` is bound to the GitHub Actions app (`integration_id` 15368). Spike S2 confirmed that a commit status with the same name can't satisfy the bound check, and that without the binding it can, so the binding is required (DECISIONS #73) | Another Actions job with the same name also comes from that app (T47) |
| T29 | **Stale approval:** a harmless commit is approved, then a malicious one is pushed | `dismiss_stale_reviews_on_push`, `require_last_push_approval`, approvals counted only on the head SHA, approvals re-run the gate | None known |
| T30 | **Writable variables and secrets:** anyone with write access can overwrite repo **and environment** variables and secrets, including those of the `pipegen-signing` environment (`PIPEGEN_COSIGN_PUB`, `PIPEGEN_COSIGN_KEY`, `PIPEGEN_FP_KEY`, `PIPEGEN_BLOCK_FROM`), and can disable workflows (spike S3). So they could swap the signing key or move the block date | These values are **not a trust root**. Verify compares the signing key against the hash recorded at install time in the owner-controlled central `pipelines` repo (CODEOWNERS-protected, T33), and a mismatch is a finding (DECISIONS #76). The gate does not compare `PIPEGEN_FP_KEY` or `PIPEGEN_BLOCK_FROM` with the install record (Plan C ruling S13): the date recorded at setup is the gate step's `block-from-recorded` literal (a protected file), and the **earlier** valid date of the two wins, so moving the variable later never delays blocking; a swapped fingerprint key only makes old findings look new (stricter). A disabled pipegen workflow is a watcher finding | A swapped value is caught at the next gate or verify run, not when it is written. With a recorded date, block-date tampering can only move blocking earlier. Central admins (T33) |
| T31 | **Verify-first checks the wrong commit** (`workflow_run`, dispatch with a ref) | The SHA comes from what is deployed. Unsupported triggers get no verify job and are listed as a gap | Deploys outside GitHub Actions |
| T32 | **AI-changed code runs with real test keys** (prompt injection through logs) | Placeholder secrets first, confirmation before real keys, code-extracted log excerpts, egress limited | A user who confirms without reading |
| T33 | **Tampering with the central repo** (malicious reusable workflows, edited install records) | A ruleset + CODEOWNERS on central, the install-record hash kept locally and in the PR body, `verify` | Central admins |
| T34 | **A tag named like a branch** passes trusted-run filters | Branch-only push triggers, and `head_sha` must be in the default branch's history | None known |
| T35 | **Abusing `not-proven`** to switch off the gate | Floor needs can never be not-proven (built into the gate). For private repos, the list lives in central | Non-floor needs marked not-proven by a code owner |
| T36 | **Scanner config auto-loaded from the repo** turns rules off | Explicit pinned configs, and declared config/ignore files are protected paths | Scanners with undocumented auto-load files (handled by review) |
| T37 | **Compat copies reach real infrastructure** (self-hosted runners, OIDC) | GitHub-hosted runners only, no `id-token`, `environment` or secrets, `contents: read` | None known |
| T38 | **The scratch repo is visible to org members** | Base-permission check and warning, delete after proof when possible, HEAD only | An org admin |
| T39 | **Runaway AI cost** | Estimate split into input/output, a hard AI cost cap (2×), prompt caching, rule-based failure classification | Estimates can be off for unusual repos |

### Added in version 5 (spikes S2 and S3, measured on real repos)

| # | Threat | Mitigation | Residual risk |
|---|---|---|---|
| T47 | **A same-name fake gate job:** a PR removes the real gate job and adds its own job named `pipegen / gate`. Every job in GitHub Actions comes from the same app (15368), so the app binding of T28 doesn't tell them apart; in spike S2 such a PR merged | A fake job can't override a failed real gate, so the attack needs the real gate removed, which changes `.github/workflows/**`. The guard is **code-owner review of `.github/workflows/**`**: CODEOWNERS plus required code-owner review are part of the floor wherever the plan allows (DECISIONS #75). The required gate check sits in its own gate-only ruleset with **no bypass**, separate from the PR-rules ruleset that carries the admin bypass for one-writer teams, so an admin bypass never skips the gate (DECISIONS #74). Verify-first finds the gate through the run of the central workflow (workflow path, `head_sha`, `event=push`, `referenced_workflows`, then the run's jobs, DECISIONS #78), not by check name | **Free private repos** have no rulesets, so there is no required code-owner review: there this is a documented limit. Solo repos: whoever can merge can also do this (T17) |
| T48 | **Capabilities assumed from the plan name:** pipegen assumes a protection exists that GitHub doesn't enforce, or skips one it does. Spike S3 found that private Free repos **do** have environments, environment secrets and variables, and deployment branch policies (against GitHub's docs), but **not** required reviewers, wait timers or attestations (422) | Capability detection **probes** each feature on the repo, never infers it from the plan name: a 422 "billing plan" answer means unavailable, and a code-scanning 404 "no analysis found" means available (DECISIONS #77). Only what the probe confirmed is relied on | GitHub can change what each plan allows without notice; probing (rather than a table of plans) keeps pipegen correct, but a change after the probe isn't seen until pipegen probes again |
| T52 | **The key-env sign job reaches a shared-CDN host while it holds the cosign key** (v0.2 Plan G G4): its egress step allows `release-assets.githubusercontent.com` (the github-releases set) so the job can download the pinned cosign release, and ghcr for the signature. E3-R3 keeps shared-CDN sets out of jobs that hold a **user** secret; the sign job holds pipegen's own signing key, so the rule does not forbid it | Besides pipegen's own steps (the cosign install, its sha256 checked when downloaded and again right before the sign step, and the sign step, which logs in with cosign itself), two reviewed actions run in that job: the pinned Bullfrog egress step (bullfrogsec/bullfrog), first, and the pinned download-artifact (the image digest). Neither step has the key in its env (only the sign step's env holds it), but Bullfrog's agent keeps running during the sign step. No repo code and no other action (the referee's sign-job allowlist, with the egress step its one exception). The block still closes every other host; github-core (github.com, api.github.com) is a wider exit than release assets anyway. The keyless sign job has no egress block, a documented exception: it needs the per-run OIDC token host (a `*.actions.githubusercontent.com` name that can not be listed exactly, and pipegen never writes a wildcard); the keyless sign job runs the pinned download-artifact (the image digest), the cosign install and the sign step, and no repo code. The attest sign job is the same exception (actions/attest needs the same token host): it runs the pinned download-artifact and actions/attest, and no repo code. Sigstore's verify hosts (`tuf-repo-cdn.sigstore.dev`, `rekor.sigstore.dev`) are a reviewed set given only to the keyless verify job; the referee refuses them in any other job, and they count as shared (anyone can write to the log), so never next to a user secret | A compromised pinned cosign or download-artifact action could send the key out over github-core or the release-assets host; the same holds without the release host. A compromised pinned Bullfrog could leave the network open, and its agent keeps running (it filters the network) while the sign step runs, with the runner's sudo, so it could read the key from that step's process; it is pinned by commit like every action, and every locked job trusts it the same way. A compromised pinned download-artifact or actions/attest in a keyless or attest sign job could send its OIDC token anywhere: it is valid for minutes and only for this run's identity |
| T53 | **Starter tests run the app's own code** (v0.2 Plan G D7): a test pipegen asks the AI to write imports the service's own modules, so it runs with the full power of that code (processes, network, files, the environment), and a malicious or injected line in either the test or the service is not stopped by the test validator. The tests also prove little: they raise a coverage floor, they do not show the code is correct | The validator (static checks of the test text, no `.skip`/`.only`, the count may not drop) is a convenience, **not the boundary**. The boundary is the CI job: starter tests run in an isolated job with **no secrets**, a **read-only token** and **egress blocked** (Bullfrog `block`, the registry only during install), and nothing from that job reaches a later job except the test result. Until the D7-R7 acceptance passes on a real runner (the f1b, f2, f3, o2, e1 and e3 probes written as hostile tests: no secret, no egress, no write token, no persisted credentials, nothing reaching later jobs), starter tests stay **off** (`isolatedTestJob` is false in the referee, the guard and `pipegen run`); a later reviewed change turns them on | Until the acceptance passes live, nothing about the isolation is proven on a real runner. Even then a green starter test says the code ran, not that it is right |
| T54 | **The nightly ZAP active scan reaches the app it scans while a job holds credentials** (v0.2 Plan G G15a): an active scan sends attack traffic, and its container runs next to the app started from the repo's own image | The run job of each pair has **no key and no secret** (no signing key, no user secret, no write token). It reaches only the app on `127.0.0.1` (`--network host`, one origin in the plan's context) behind the egress block, its container drops all capabilities, and its raw result travels to a **separate scrub job** (pipegen's own gate action in scrub mode, no repo code) that removes secret-looking text before the upload job sends the scrubbed file to code scanning. The scan is reported and never gating. The ZAP API answers only 127.0.0.1 (G17B-R1: `-config api.addrs.addr.name=127.0.0.1 -config api.addrs.addr.regex=false` on every ZAP command pipegen renders, the baseline scan of the merge layer included), so the scanned app, on its own bridge network, can not drive ZAP's keyless API (delete its alerts, switch its scanners off, run scripts in ZAP). The app containers drop every capability and gain no privilege; the dependency containers gain no privilege | The app under scan can answer with data a real secret would be inside (the scrub removes what it recognises, not everything), and the scan can take up to its 45-minute ceiling of runner time. Neither is proven on a real runner until live items 24 to 26 of `docs/smoke-test.md` pass. With pipegen's compose file, the compose start builds the app's image inside the DAST run job (the Dockerfile's RUN steps run there under BuildKit's own capabilities), a second build of the same Dockerfile: DAST scans that build, not the archive the image scan reads. The run job holds no key, secret or write token |
| T55 | **An edited install record turns uninstall into a delete tool** (v0.2 Plan V): the record lives in the central repo, so anyone with write access there can edit it to name an object pipegen never made (a ruleset, a secret, a file, a repo) and wait for the next `pipegen uninstall` | The record is read only through the trust check (`trustedPrevious`): an untrusted record stops uninstall, a typed trust acts on the view's entries only and everything the view drops is a manual step, and the marker in the PR body is never trust. An object is deleted **only when the record lists it as created and GitHub's current id and `created_at` equal the recorded ones**; anything else is kept and listed ("not the one pipegen created"), whatever a hash says. The record parses against a strict schema (unknown keys, duplicates, prototype keys and depth are refused). A path claim must be a path pipegen creates (`createdPathProblem`, the project's own central name); every recorded edit must match one of pipegen's builder forms before it is reverted, otherwise it is manual; the exact central file list is the record's central files that belong to this project, never a glob. Names are typed at the user's own terminal (no flag, no variable and no missing terminal can answer them) for `unconfirmed` objects, the app's own secret names, `adopted` files and every repo delete, and nothing the repo or the record says is put into a question | A user who types the name of something pipegen didn't make deletes it: the preview and the typed name are the guard. A central admin can change or delete files by hand (T33). Token mode never deletes a repo; it prints `gh repo delete` only after the checks the App's delete uses |

### The user's machine running the CLI (v0.1 audit and every later command)

| # | Threat | Mitigation | Residual risk |
|---|---|---|---|
| T40 | **A compromised dependency of pipegen** runs on the user's machine (`npx` resolves version ranges) | All dependencies are **bundled** into `dist` (zero runtime `dependencies`), trusted publishing, a 7-day cooldown for build dependencies | A compromised build-time dependency at release time (cooldown + review) |
| T41 | **A hostile repo redirects `npx`** (its own `.npmrc`: a registry, `node-options`, a script shell; a local `node_modules/.bin/pipegen`; a committed `node_modules`), so `npx pipegen` inside the folder runs something other than pipegen | **Normal use** is `npx pipegen` inside your own project folder (DECISIONS #124). **Safe mode**, for a repo you don't trust, runs pipegen from outside it with `--dir`, an exact version and an explicit `--registry`; the README and `--help` name it. **The stop:** before anything else (before the `--ai` checks, any read of the repo, the type question or any GitHub call), `pipegen` and `pipegen inspect` check the folders npm read when it started them (npm reads the `.npmrc` of the nearest folder with a `package.json` or `node_modules`, which can be a sub-folder): every folder from the current one up to the audited repo when it is inside it, and, whatever `--dir` says, every folder from the current one up to the higher of the nearest one that holds `.git` and npm's own project folder (npm doesn't stop at `.git`), plus every folder up the way for a `node_modules/.bin/pipegen`; never the home folder or above it (`~/.npmrc` is the user's own config). In each: an `.npmrc` with any key outside a short safe list (one that can't be read safely counts), a `node_modules/.bin/pipegen`, or a committed `node_modules`: one on disk counts unless the git index of the nearest repo proves it isn't committed, and one the index lists counts under any name a file system could read as `node_modules` (names compared folded: NFKC, case folded with `ſ` as `s`, invisible characters removed; on macOS and Windows `Node_Modules` is `node_modules`). If one is found, pipegen says what it found, prints the safe-mode command and exits with code 4. Run from outside, the same findings are a warning at the top of the report. pipegen's own child processes get explicit environments, so npm's `npm_config_*` variables don't reach them | **A hostile repo can still run its own fake pipegen first**: if npx runs the repo's package instead of pipegen, pipegen never starts and can't stop it. **A repo `.npmrc` can make npm load the repo's own code into pipegen before it starts** (for example `node-options`); pipegen stops right after, but that code has already run. Only safe mode avoids both. Folders above the higher of the current repo's top and npm's project folder are checked only for a local pipegen, and the home folder and the folders above it not at all; an npm workspace root further up that lists the folder (npm 7+ reads its `.npmrc` too) is not found: start pipegen from a folder you trust. A user who runs a stranger's repo without safe mode |
| T42 | **`--out` writes through a symlink** (e.g. into `~/.bashrc`) | No-follow + exclusive create, symlinks refused, default output location outside the repo | None known |
| T43 | **Terminal / Markdown injection** from repo-controlled names (ANSI/OSC escape codes, bidi, links) | Every repo- or AI-derived string goes through `safeText`/`safeMarkdown` | New terminal features (regular fixture updates) |
| T44 | **Parser or regex denial of service** (YAML alias bombs, huge files, very long lines) | 1 MB file limit, 20k file limit, `maxAliasCount`, line-length limit for regexes, no child processes during the audit without `--ai`; with `--ai`, only the pinned, checksum-verified secret scanner (betterleaks, or the gitleaks fallback) | Slow but bounded runs on huge repos |
| T45 | **Token leak** (sent to a wrong host, printed in errors or JSON) | Hard-coded `api.github.com`, never printed, tests on `--json`/`--out` | None known |
| T46 | **AI key leak** (`ANTHROPIC_API_KEY` / `OPENAI_API_KEY` sent to a wrong host, or shown in errors) | Keys are read only from the environment pipegen is given, never from the repo. Claude uses a hard-coded `https://api.anthropic.com` (`ANTHROPIC_BASE_URL` and `ANTHROPIC_AUTH_TOKEN` are ignored), OpenAI a hard-coded `https://api.openai.com/v1/chat/completions`, and Ollama gets no key. Error messages are pipegen's own text, never a response body (OpenAI echoes part of a wrong key). Tests build keys at runtime and check every error. The Anthropic SDK's OpenTelemetry tracing is turned off in code (no spans, no trace headers), so a tracer the user has loaded can't export prompts that hold repo code | The Anthropic SDK also adds the headers listed in the user's own `ANTHROPIC_CUSTOM_HEADERS` variable to every Claude request, and it has no switch to turn that off. Those headers still go only to `api.anthropic.com`, and they come from the user's environment, not the repo |
| T49 | **The tool cache is swapped between the hash check and the run** (another process replaces `~/.cache/pipegen/tools/<tool>-<version>/<tool>` after pipegen hashed it and before it starts it, with `audit --ai`) | The cached binary is hashed again through one file descriptor (opened without following a symlink) before every use; a mismatch deletes it and nothing runs. Every directory from the tool folder up to `/` must belong to the user (or root) and be writable by nobody else (not by its group, not by others); the one exception is a root-owned sticky directory above pipegen's own folders, such as `/tmp`, where others can't replace what they don't own. So no other user can swap it. Downloads are written to a temp file and renamed into place | A process that already runs as the same user can still swap the file in the short window between the hash check and the exec (the run uses the path, not the checked descriptor). Accepted (Plan P T7 M4): such a process can already change the user's shell, PATH or pipegen itself, so a compromised user account is out of scope |
| T50 | **A secret used as a file or folder name is printed** (an `audit --ai` report, or the consent screen) | In an `audit --ai` run every listed name goes into the secret scan's file list as several lines: the name (also from every `/ - _ + =` in it), each path segment on its own line, and pipegen's own decodings of it (every base64/base64url run at all four alignments, every hex run at both, percent-escapes), so finding an encoded secret doesn't depend on where the scanners start a token (P48). A name that would need more than 48 extra lines, or past 200,000 in all, is hidden instead. A belt hides a name with a high-entropy run (20+ base64 characters with letters and digits, at least 3.5 bits per character, 3.0 for hex) whatever the scanner says: 0.03% of 36,862 real file names, 92% of random secrets. Whatever is found (a flagged name whole; a found value, or the encoded text of a decoded name finding, anywhere) is masked in every terminal, JSON and Markdown string before any cut, and a name longer than the scanner reads (1,000 characters) is hidden whole (P40, P45) | The consent screen is shown before the scan, so it lists the counted top folders unscanned: a folder named after a secret is printed there (on the user's own terminal only: consent needs a TTY, nothing is sent). A plain `audit` (no `--ai`) runs no scanner, so only redact()'s patterns hide names. A secret no scanner rule knows, in a short or low-entropy name, or under an encoding pipegen doesn't decode (nested, compressed, other alphabets), is not found |
| T51 | **A folder of the repo is swapped for a link while pipegen reads a file** (a second local process that can write to the repo folder, during an audit), so the read lands outside the repo | Every repo file is read through readTextLimitedWithReason, and every lockfile through readLinesLimited, with the repo root (both share the same checks): no level may be a link (checked before and after the open), the open never follows a last-level link and never blocks, fstat must match the checked file, and on Linux the opened descriptor's own path (/proc/self/fd) must be inside the root's real path (P46a, P49). Measured: 1.4 million renameat2 swaps in 25 s, no read outside the repo (before P49: 133 in 8 s) | Without /proc (Linux with /proc not mounted), on macOS (Node does not expose O_NOFOLLOW_ANY, so the open can't refuse a link at every level) and on Windows, only the path checks remain, and a process that swaps a folder back and forth fast enough can still win between two of them. Accepted for v0.1: the attacker needs write access to the repo folder while the audit runs, which is usually the user or a process running as the user (who can read the outside file anyway); a shared or group-writable repo folder widens this. What pipegen would do with the file is put facts from it in the report or (with `--ai`) the secret-scanned bundle |

**Known limits of the `.gitignore` support (DECISIONS #126).** pipegen reads `.gitignore` files, `.git/info/exclude`
and the git index itself (no git process), and reads `info/exclude` and the index only when `.git` is a real folder
(not a link, not a `.git` file). Two cases follow from that:
- **A git submodule:** the repo's index lists only the submodule's commit, not its files. A file committed in the
  submodule that the submodule's own `.gitignore` lists therefore reads as "not committed and ignored", and the quick
  secret check (advisory) skips it. The AI bundle leaves every submodule file out when the index is known, which is safe.
- **A linked worktree** (`git worktree add`): `.git` is a file there, so pipegen has no index, and the worktree's shared
  `info/exclude` (kept in the main repo's `.git` folder) and the user's `core.excludesFile` are not applied: a file the
  user excludes only there would reach the AI bundle. Today's audit refuses a worktree (it reads the remote from a
  real `.git` folder only), so this applies once a later command reads worktrees. Without an index, a `node_modules`
  folder in a worktree counts as committed for T41's stop, and the stop says the folder is a worktree.

## Out of scope (v3)

Malicious GitHub staff or infrastructure. A compromised user machine. Attacks on the AI providers themselves. Making a malicious repo look clean on purpose (pipegen protects pipelines, it doesn't certify code).
